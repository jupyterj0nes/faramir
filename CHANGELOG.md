# Changelog

## Unreleased

### Clean hives are memory-mapped: the Windows techniques run ten times faster on the same memory

- **A clean hive is read through a memory map** (`memmap2`) instead of a buffered file. The 55 techniques seek through a hive thousands of times; through `BufReader` every seek threw the buffer away and became a system call, through the map it is a memory read. Nothing is loaded up front: the operating system brings each 4 KiB page in the first time a technique touches it and drops pages again under memory pressure, so a machine with little RAM is no worse off than before and a 500 MB SOFTWARE costs no resident memory beyond the pages in use. Measured against the 0.4.0 binary on the carving-lab VHD: live analysis 5.6 s of CPU to 0.5 s, with `--carve` 15.7 s to 1.3 s, peak working set 48 MB to 49 MB; the Linux samples do not change (no hives). The CSVs are identical byte for byte, except the rows whose `timestamp` and temporary path already changed from run to run before (startup folder, GPO script, forced extension: see the pending note in the 0.4.0 entry).
- **A dirty hive costs its size once, not twice.** The replayed copy is all the techniques read; the on-disk bytes and the transaction logs are released before the hive is parsed, where they used to live for the whole analysis of the host.
- When a hive cannot be mapped, **3050 `ERR_WIN_HIVE_MAP`** (warning) is recorded and the hive is read through the buffered file as before: same bytes, same result, slower. A missing or unreadable hive is still 3001.
- Tests: `tests/test_hive_mmap.rs` (a readable hive is mapped; the map and the buffered file return the same bytes at every offset the techniques land on; the techniques find the same values through the map; an empty file maps to nothing and a missing one is an open error), 3050 in the catalogue and the dense-range check.

## 0.4.0 (2026-11-05)

### Faramir's own header: 19 columns in masstin's verticals, nothing dropped

- **The header is faramir's.** `timestamp,computer,artifact,event_id,state,target_username,reserved_1,processname,reserved_2,subject_username,reserved_3,pid,commandline,source_file` and the shared tail. Same width as masstin's timeline and the same verticals (`timestamp` under `time_created`, `artifact` under `event_type`, `commandline` under `detail`, `source_file` under `log_filename`, `target_username`/`subject_username` under the user columns), but each column named for what faramir puts in it, so the file is readable on its own and a case tool can tell the two tools apart by the header. The three verticals persistence has nothing for (`target_domain_name`, `src_ip`, `subject_domain_name`) are `reserved_1..3`, always empty. The earlier build of this tail copied masstin's header name for name; that is gone.
- **Nothing the event carries is dropped any more.** `state` (`live`, `deleted`, `removed_since_vss`, `carved`, `carved_deleted`, `previous_version`), `processname` (the image name) and `pid` (the process id of a running-process row) now have their own columns; the previous layout left them out.
- **`source_file` is the file the entry was read from, relative to the evidence, and the key inside it**, the equivalent of masstin's `log_filename`: `/etc/cron.d/e2scrub_all`, `/home/bob/.ssh/authorized_keys`, `/lib/systemd/system/nginx.service`, `partition_0\Users\bob_NTUSER.DAT:deleted key Software\Microsoft\Windows\CurrentVersion\Run`, `VSS snapshot created …, gone from live volume: partition_0_vss_0\Users\mallory_NTUSER.DAT`. On Windows the engine already stamped every finding with its origin file and never wrote it; on Linux the column used to hold the daemon's name (`crond`, `systemd`, `sshd`…), which `artifact` already says. The extraction folder of a disk image (`…\Temp\faramir_img_<pid>_0\…`) no longer appears in the column: paths are relative to the evidence root, as the Linux parsers always wrote them.
- **The file name leaves `commandline`.** `System Cron: … (File: /etc/cron.d/x)` is `System Cron: …`, `Sudoers [90-cloud-init-users line 4]: …` is `Sudoers [line 4]: …` (same for PAM, APT, udev, modprobe and the modules file); the file, now with its full path where the old text had the base name only, is in `source_file`. Line numbers stay. The hunt's identity reads the command alone, so the clean reference and `--known-good` CSVs match as before; the hunt's location check for packaged systemd units now sees the unit's path (a unit under `/etc/systemd/system` is no longer called packaged; it stays `habitual` when the clean reference carries it).
- Measured on the samples against the previous build: Ubuntu triage, 767 rows, every event column other than `commandline` identical, `hunt` and `hunt_score` identical on every row, `commandline` changed only by the file-name removal (462 rows); carving-lab image, 10 rows, same states and scores, and no temporary path left in `source_file`.
- `src/hunt/clean/windows.csv` and `linux.csv` are compiled into the binary and were ignored by `.gitignore` (`*.csv`): a fresh clone did not build. They are tracked now.

### A clean host vouches by identity; four emitters fixed; measured on clean and planted hosts

- **The clean reference is built in** (`src/hunt/clean/windows.csv`, `linux.csv`, written by `scripts/measure_clean.py` from the two clean lab hosts of the reference: 861 Windows and 764 Linux entries, the lab's beacon and the collection's activity left out). An entry a clean host carries, like one in a `--known-good` CSV, is `habitual` whatever its rules say: the rules keep their clause, add no points, give no state, and a deleted or carved state no longer forces `candidate` on it. Matching is by the same identity as before, now also with version folders neutralised (`\Platform\4.18.26100.4-0\` is `\Platform\<ver>\`). The stock pattern lists keep their weaker meaning (a high rule overrides them). `hunt_why` says `on the clean reference hosts`; the summary line counts them apart from `known-good`.
- **Four emitters wrote a label where the hunt reads what runs.** Office add-ins (`detail` was `ProgID (FriendlyName) -> dll`, read as an alternate data stream; now the dll or manifest, the label in `log_filename`), AeDebug (`AutoExclusionList\DWM.exe = 1` was reported as a debugger; subkeys now yield `Debugger` values only), IFEO (`log_filename` repeated the debugger instead of naming the hijacked image; now `…\Image File Execution Options\sethc.exe\Debugger`), scheduled tasks (TaskCache rows carried the task's path, read as an image in the drive root or as an obfuscated payload; they now carry the command of the task's XML when the Tasks folder is in the evidence, and XML files in folders under `Tasks`, where most Microsoft tasks live, are now read; a TaskCache row whose XML is absent keeps the path and runs nothing for the rules).
- **Measured.** Two clean Windows Server 2016 hosts: from 6 `significant` and 19 `candidate` each to none but the lab's own beacon task on the member server. Clean Ubuntu 22.04: one `candidate`, the lab's own sudoers line. Out of sample (reference from one host, the other judged): one `candidate`, a DC-only deleted policy script. Planted domain controller (`scripts/lab/plant.ps1`): Eight of the nine came out flagged, seven `significant` and the service `candidate`, nine rows in all and not one of them unplanted; the miss is the WMI event consumer, a technique faramir does not read yet (caarea sees what it launches).

### Fixed

- **The hunt reads what runs.** Services, service DLLs, TaskCache tasks, App Paths, the Startup folder, Group Policy extension DLLs, AeDebug, WER, Winlogon Shell and Userinit, Explorer Load, the CHM helper, AppCertDlls and the cmd AutoRun put a label in `detail` (`ServiceDlls`, `Startup Folder`, `Scheduled Task`, the service's display name) and the command in `log_filename`, so the hunt, which reads `detail`, judged the label. `detail` now carries the command, image, DLL or value and `log_filename` the key or file it was found in (`Services\Spooler (Print Spooler)`, `Microsoft\Windows NT\CurrentVersion\Winlogon\Shell`), as the column table always said. On a clean Server 2016 the old layout made the alternate-data-stream rule fire on 272 of 502 services, the `,-1000` of a MUI display name taken for a stream; it fires on none now, and 1,502 of the 2,004 rows of two clean hosts match the stock lists instead of 43.

### Hunting: every row gets masstin's analysis tail

- **One CSV, 19 columns, as wide as masstin's timeline** (the header is faramir's own, see above): 14 event columns in masstin's verticals and the analysis tail `hunt`, `hunt_score`, `hunt_why`, `verdict`, `notes`. Quoting is masstin's: an empty event field is `""`, a value is quoted only when it holds a comma, a quote or a line break, the tail is bare when empty.
- **The tail follows the convention shared by masstin, caarea, faramir and allymacb** (masstin `docs/csv-format.md`, "The same tail in caarea, faramir and allymacb"). `hunt` takes six words only: `significant`, `candidate`, `habitual`, `not_evaluated`, `baseline` or empty. The state comes from the strongest evidence: a high rule writes `significant`, a medium rule `candidate`, a low rule leaves the statistical state as it is; when a test and a rule both speak, the stronger state wins. `suspicious` is the analyst's word, in `verdict`.
- **`hunt_why` names the source.** A rule's clause starts with its id and level, `rule H1001 (high): LOLBin fetching remote content [T1218]`; the test's clause and the rest are in words. Rules first, strongest first, clauses separated by `; `. A reader filters `hunt_why` on `rule ` for the catalogue, on its absence for the statistics.
- **`hunt_score` is masstin's rarity, 0 to 100.** The test contributes −10·log10(q); every rule that fired adds its points in the same unit, measured per rule and per system on clean reference hosts, never chosen by level (`src/hunt/measured.rs`: two Windows Server 2016 lab hosts, 2,003 rows; an Ubuntu lab host, 761 rows); a pattern that never fired gets the bound the reference gives, 33 on Windows and 29 on Linux; a rule measured below 10 points is noise on that system and gives neither state nor points; contributions add, capped at 100; `habitual` and `baseline` rows are 0.
- **Two engines.** A rule catalogue (`src/hunt/rules.rs`, `H1xxx` Windows, `H2xxx` Linux, `H3xxx` both) of what known-bad persistence looks like, calibrated against real stock Ubuntu and Windows rows (no high rule fires on a stock host), and the stock lists of what Windows, Debian, Ubuntu and RHEL ship with; and masstin's statistical test applied to persistence rows: conformal p-value against the run's own reference rows, Benjamini-Hochberg across the run at `--alpha` (default 0.05).
- **Switches.** `--baseline <date>` (alias `--investigation-from`): rows before it are the reference, rows after it are put to the test. `--alpha <q>`. `--no-hunt` leaves the three hunt columns empty. `--known-good <CSV>` (repeatable) counts a clean host's entries as known good. `--carry-marks <CSV>` (repeatable) copies the analyst's `verdict` and `notes` from an earlier CSV onto every row with the same 14 event columns (masstin's row hash).
- **Error codes 7001–7014, category HUNT**, in the catalogue and the diagnostics summary: invalid baseline or alpha, known-good and carry-marks files that cannot be read or are not a timeline, unparseable timestamps, single host without baseline, techniques without reference rows, rows after the baseline, hunt disabled, hunt summary.
- Tests: `tests/test_hunt.rs` (CLI, header byte for byte, 19 columns, every rule has a row that fires it, stock rows never flagged, classic attacks always flagged, the words and the shape of `hunt_why`) plus unit tests in every hunt module.
